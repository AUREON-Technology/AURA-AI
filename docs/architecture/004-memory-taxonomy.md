# ADR-004 — Six memory kinds with distinct lifecycles

**Status:** Accepted · **Date:** 2026-08-02

## Context

Today there is one memory kind: an LLM-extracted "user fact" stored in the same Qdrant collection as
document chunks, distinguished by a `type` payload field. Facts accumulate forever. Duplicates are
deduplicated only by exact-text hash (`services/deterministic_id.py`). Contradictions
("the user lives in Cairo" / "the user lives in Berlin") coexist and are both retrieved. There is no
conversation state on the server at all — the client re-sends history on every request.

Different kinds of memory have genuinely different lifecycles, and forcing them into one store
produces wrong behaviour for most of them.

## Decision

Six kinds, one retrieval facade (`memory/engine.py`), distinct policies:

| Kind | Holds | Scope | Lifecycle | Store |
| --- | --- | --- | --- | --- |
| **Working** | the current turn's scratchpad: plan state, tool results, intermediate reasoning | one request | discarded at end of turn | in-process |
| **Episodic** | conversation turns | session | rolling window + running summary; TTL 30 d | Redis + Postgres |
| **Semantic** | durable facts about the user, with provenance and confidence | user | consolidated, decayed, superseded | Postgres + vector index |
| **Entity** | people, projects, places the user refers to, and their attributes | user | updated on mention; feeds the knowledge graph | Postgres + graph |
| **Procedural** | learned preferences about *how* to do things ("always summarise in bullets") | user | reinforced on repetition, decayed on disuse | Postgres |
| **Reflection** | the assistant's own conclusions about past interactions | user | generated by the reflection job, never by the user | Postgres + vector index |

**Common contract.** Every record carries `id`, `kind`, `owner_id`, `content`, `embedding_ref`,
`confidence`, `provenance` (turn id, source, extractor version), `created_at`, `last_accessed_at`,
`access_count`, `superseded_by`, `expires_at`.

**Retrieval score** blends semantic similarity, recency, and reinforcement — the same three signals
used by the generative-agent literature — with per-kind weights:

```
score = w_sim · cosine + w_rec · exp(-Δt / τ_kind) + w_use · log1p(access_count)
```

**Consolidation** (`memory/consolidation.py`) runs on a schedule and:
- merges near-duplicates (cosine ≥ 0.94) into one record, summing `access_count`,
- detects contradictions within a `subject` and marks the older record `superseded_by` the newer
  rather than deleting it (auditability, and the user may correct the newer one),
- decays confidence for records untouched past `τ_kind`, and expires those below a floor.

**Write-time corrections (2026-11-22).** A write that lands near an existing record
(`MemoryEngine.remember`) is reconciled at once rather than waiting for consolidation:
- the same words reinforce the stored record;
- different words about the **same `subject`** are a correction: the old record is marked
  `superseded_by` the new one (kept for audit and erasure, hidden from recall), unless the new write is
  less trusted than the stored one (the person's own write outranks `remember_fact`, which outranks
  anything else), in which case the stored record stands;
- a write with no `subject` inherits the old record's subject;
- a near-duplicate about a **different subject**, or a stored record with **no subject**, is a different
  fact and both stay active. Two memories can embed close together without saying the same thing.

**Writes are explicit and attributable.** Nothing is written to semantic memory without a provenance
record naming the turn and the extractor version, so a bad extractor version can be rolled back by
query.

## Encryption at rest (P1.2 / P5.1)

**What it is.** Server-side, application-level authenticated encryption of the free-text payload
of two Postgres tables: `aura_memories.content` and `aura_personal_os_records.fields`. It is
**not end-to-end encryption**: the gateway and workers hold the key and decrypt on every read,
because recall and the personal-OS tools must hand these values to the model. What it protects
against is exposure of the *database* — a dump, a backup file, a copied volume, a read-only SQL
credential — not a compromised application server. The synced tables
(`tasks`/`calendar_events`/`finance_records`/`health_records`/...) are not covered by this
encryption. They used to be zero-knowledge, encrypted on the client with a key the server never
had. That ended with ADR-032: their `*_enc` fields are now AES-GCM under a per-user data key,
which the server holds wrapped by these same keys. The keys are therefore also the
key-encryption key for every user's data key, and `scripts/reencrypt_fields.py` re-wraps those
keys on rotation.

**Mechanism** (`aura_core/adapters/field_crypto.py`). Fernet (AES-128-CBC + HMAC-SHA256) from the
already-required `cryptography` package, under its own key, separate from
`AURA_SECRETS_ENCRYPTION_KEY` (third-party tokens) because the two have very different loss
consequences. Stored form: `aura-enc:v1:<key-id>:<fernet-token>` in the `TEXT` column, and
`{"_aura_enc": "aura-enc:v1:…"}` in the `JSONB` column — no schema change and no migration. The
authenticated plaintext is bound to its row (`table:id:owner`), so ciphertext copied into another
row is rejected rather than read as that row's data.

**Keys and rotation.** `AURA_DATA_ENCRYPTION_KEYS` (Docker secret
`deploy/secrets/data_encryption_keys`, hydrated from `AURA_DATA_ENCRYPTION_KEYS_FILE`) is a
comma/newline-separated list, newest first: the first key encrypts, every key decrypts. Rotation
is: prepend a new key → restart → `python scripts/reencrypt_fields.py` (idempotent, batched,
owner-agnostic, `--dry-run`) → drop the old key once the script reports nothing left under it.
Keys are loaded only in `container.build_field_cipher`; the adapters receive a cipher.

**Failure behaviour.**

| Situation | Behaviour |
| --- | --- |
| staging/production, no key | Refuses to start (`AuraSettings.validate`, repeated in `build_field_cipher`). Fail-closed: the alternative is silently storing personal data in plaintext. |
| local/development/test, no key | Plaintext passthrough with a startup warning. In-memory adapters are always plaintext (process-local). |
| Any environment, a key that is not a valid Fernet key | Refuses to start. |
| Legacy plaintext row (written before a key existed) | Read as-is; sealed on its next write, or in bulk by the script. |
| Encrypted row, no key configured | `ConfigurationError` — never returns ciphertext as content. |
| Tampered / truncated / moved ciphertext, or key no longer configured | `DataIntegrityError` (`kind="data_integrity_error"`, not retryable). |

**What stays in the clear, deliberately.** Everything a query filters, sorts, joins, or counts
on: ids, `owner_id`, `kind`, timestamps, `confidence`, `access_count`, `superseded_by`,
`expires_at`, all `prov_*` provenance columns, memory `subject` (a ≤64-char topic label used as
an exact-match filter and for contradiction grouping), memory `metadata`, and personal-OS
`source`. `subject` in particular can reveal *what kind* of fact is stored ("health", "diet")
without its content.

**Capability lost.** No SQL over the sealed columns: no `ILIKE`/full-text on memory content, no
`fields->>'x'` predicates on personal-OS records. At the time of this change no such query
existed (recall is vector similarity in Qdrant followed by `get_many` by id; personal-OS listing
filters only on owner/kind), so nothing served today regressed. Any future content filter must
run in Python after decryption, bounded by an owner/kind/time predicate that *can* run in SQL.

**Residual leakage — stated, not hidden.**
- **Embeddings.** Each memory's embedding lives in Qdrant (plaintext vector, with `owner_id`,
  `kind`, and `subject` in its payload). Embeddings are derived from the content and are known to
  be partially invertible; anyone who can read the Qdrant volume learns approximately what a
  memory says. Encrypting the vector store is out of scope here.
- **Other tables are unchanged:** `aura_documents`/`aura_chunks` (knowledge-base text),
  `aura_feedback` (prompts/responses/corrections), graph entities/relations, telemetry, and the
  session/episodic stores remain plaintext.
- **Length and timing.** Ciphertext length tracks plaintext length; write times are visible.
- **Dev and prod share `deploy/secrets/`**, so on the shared VPS both stacks use the same data key.

## Alternatives rejected

| Alternative | Why rejected |
| --- | --- |
| Keep one kind, add tags | Tags don't give different decay, consolidation, or retrieval weighting. The behaviour differences are the point. |
| Store everything in the vector DB | Vector stores are poor at the relational questions memory needs ("all facts about entity X superseded after date Y"). Vectors index; Postgres is the source of truth. |
| Summarise the whole history into one blob | Loses provenance, cannot be corrected, and degrades unpredictably as it is repeatedly re-summarised. |
| No server-side conversation memory (status quo) | Makes the assistant stateless across devices, forces the client to hold and re-upload history, and makes the token budget the client's problem. |

## Consequences

**Positive** — recall improves because retrieval weights differ per kind; contradictions resolve;
memory can be shown to the user and edited with provenance; the token budget for memory is bounded
and predictable.

**Negative** — six concepts instead of one, and consolidation is a background job that must be
monitored. Mitigated by the facade: callers use `memory.recall(query, kinds=..., budget=...)` and
never touch a store directly.

**Impact:** maintainability improved (each policy is isolated and testable); cost slightly higher
(more rows, one scheduled job) but token cost lower because retrieval is more precise; security
improved because provenance makes it possible to purge everything derived from a given source.
