## 3. Database audit

**Schema authority.** Alembic `0001`→`0019` is a single linear chain (every `down_revision` read; `0019` revises `0018`). `0016` baselines the 16 runtime-created `aura_*` tables and carries 21 `CREATE INDEX` statements copied from the adapters; `tests/architecture/test_runtime_tables_have_migrations.py` is claimed to pin adapter DDL to the migration text (not run here). Adapters still execute `CREATE TABLE/INDEX IF NOT EXISTS` on first use (`postgres_store.py:125-135`), so the schema has two writers that are kept equal by a test rather than by one source of truth — acceptable, but a drift in either direction is only caught if that test runs (CI is not executing, CB-44).

**Pool concurrency (prior concern).** `PostgresPool._get_pool` is now a double-checked `asyncio.Lock` (`postgres_store.py:94-124`): concurrent first callers build exactly one pool. `_ensure_schema` deliberately runs outside the lock; its statements are all `IF NOT EXISTS`, so racers converge. **Resolved.** Residuals: no `command_timeout` or `statement_cache` option on `create_pool` (`:120-122`), so a hung statement holds a connection for the connection's lifetime; the legacy SQLAlchemy engine (`infrastructure/db/base.py:69`, `pool_pre_ping=True`) is a second pool per worker that the container never disposes (BACKEND_STATUS.md:160-161 admits this). Pool budget: 2–10 asyncpg + SQLAlchemy default 5+10 per uvicorn worker × `AURA_WORKERS` (default 4, `Dockerfile:147`) plus every Celery worker; no `max_connections` is set in either compose file and nothing computes the total (`container.py:905` only names the risk).

**Encryption at rest.** `FieldCipher` (Fernet, context-bound plaintext) seals memory `content` (`postgres_store.py:831-895`), personal-OS records, connector credentials and the per-user DEKs (`user_data_keys.py:64-110`; migration `0019`). `AURA_DATA_ENCRYPTION_KEYS` is required in production-like environments (`settings.py:1882-1901`). A stored value without the `aura-enc:v1:` marker is read as legacy plaintext (`field_crypto.py:33-36,180-182`), so a deployment that gained keys later keeps old plaintext until `scripts/reencrypt_fields.py` runs — `UNKNOWN` whether that has ever run on Railway. **Not encrypted:** `aura_documents`/`aura_chunks` text and Qdrant payloads (no cipher on the document store; the Railway target's Qdrant is a third-party cloud, `docs/deployment/control-plane.md:69`). ADR-032 (Option A) states plainly that synced personal-OS fields are no longer zero-knowledge (`032-personal-os-single-store.md:325-335`); the DEK endpoint (`v3.py:1192-1252`) is TLS-only, per-user rate-limited (10), audited by kid only, and refused to service keys.

**Integrity and ownership.** Every `aura_*` table keys rows by a `TEXT owner_id` with no foreign key to `users` except `aura_user_data_keys` (`0019:32-33`, `ON DELETE CASCADE`). Erasure is therefore application-driven (`admin_platform.py:245-292`): memories+vectors, documents+chunks+graph, personal-OS (synced and legacy), transcripts, then the `users` row. What it does not reach is declared (`NOT_ERASED`, `:234-242`): feedback, turn telemetry, audit log, agent run history, LLM cache, idempotency keys, unsynced transcripts. Of these, the audit log carries `actor` (email) and `source_ip` (`0016:64-75`) with **no retention or purge path** (grep for retention/purge finds only idempotency, learning indexes and outbox).

**SQL construction.** Every f-string in `postgres_*.py` interpolates module constants (`_COLUMNS`, `table.name` from a fixed `TABLES` map, `' AND '.join(clauses)` built from fixed clause strings with `$n` placeholders) — `postgres_store.py:1055-1056`, `postgres_synced_personal_os.py:295-441`, `postgres_models.py:154`, `postgres_approvals.py:148`, `postgres_service_keys.py:79-96`. Connector profiling quotes identifiers (`connectors/postgres_catalog.py:241-257` uses `ident` from `quote_identifier`). **No injection path found.**

**Backups.** VPS only: `pg_dump --format=custom`, Qdrant snapshot, Redis, age-encrypted, retention by day/week/month, offsite via rclone (`backup.sh`, compose `:1195-1244`). The Railway target has no backup job in the repo (`control-plane.md` has no backup/restore mention); whatever Railway's Postgres plugin does is `UNKNOWN`. The backup container mounts the whole `deploy/secrets` directory (finding F1-02).
